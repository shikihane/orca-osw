# Orca 1.4.246: worker-show views, worker-start receipt, inbox rows, and omp readiness

Measured 2026-11-03 against the installed Orca (app + `resources/bin/orca.exe`
1.4.246, runtime reachable, `osw doctor` OK). Every claim below was produced
by running the CLI; the payloads are reproduced verbatim where short.

## 1. `orchestration worker-show` has two shapes

Without `--full`, the command prints one flat agent-facing row:

```json
{"dispatchId": "ctx_1946e90a5fa2", "taskId": "task_70a3d30ae4b0",
 "runId": "run_b1287061d77d", "state": "unsupervised", "stage": "context_only",
 "liveness": "unverifiable", "terminal": "term_...", "attention": ["failure"],
 "waitingOnHuman": "unknown", "lastError": "Agent exited with code -1"}
```

The nested records OSW's settlement view reads (`dispatch`, `worker`,
`projection`, `observation`) only exist with `--full`, which is the unchanged
raw result. The view builder is
`resources/app.asar.unpacked/out/cli/handlers/orchestration/worker-agent-views.js`;
the flat row is `WORKER_SHOW_VIEW.fields`.

Before this change, `worker_settlement` raised `orca_contract_mismatch` on
every poll, and `_run_supervised` treated that as a transient hiccup: the
watcher re-polled until `HARD_TIMEOUT_SECS` (1h) and the task looked hung.
Two OSW fixes: request `--full`, and treat a contract mismatch as terminal
(the task fails now, with the message in the report).

Settlement vocabulary, from `out/shared/orchestration-fleet-outcome-resolution.js`
and the daemon's own state lists: a Dispatch ends `completed`, `failed`
or `circuit_broken`; a worker row ends `succeeded`, `failed`, `stopped`
or `abandoned`; `unsupervised` is the pre-v3 worker state and says nothing
on its own. `observation.agentWait`, when present, is an object
(`{reason, source}`), not a string; the flat view renders it as
`waitingOnHuman`.

## 2. `worker-start` receipts carry `terminal`, not `effects`

The concise receipt of a real start:

```json
{"dispatchId": "ctx_667e18d383fb", "taskId": "task_306da1c6e2b8",
 "runId": "run_1ce1d5329783", "runCreated": true, "state": "failed",
 "agent": "omp", "mode": "terminal", "terminal": "term_777c588d-...",
 "workspace": "...", "failedStage": "agent_readiness", "lastError": "timeout",
 "residualResources": ["terminal term_777c588d-..."],
 "next": "This start created a terminal that never ran the Task. Close it with: ..."}
```

`effects` is a `--full`-only field, so `worker_start_receipt` (which looked
only at the terminal effect) found no handle and `new` aborted with
"worker-start returned no agent terminal". `--full` is not an option for
`worker-start`: it also turns "turn not yet observed" into exit 1, which
OSW relies on as exit 0.

## 3. Inbox rows renamed their sender fields

`orchestration inbox --json` rows are now the consolidated message view
(`message-agent-views.js#toMessageView` + `inboxRowView`):

```json
{"id": "msg_0be382053cbd", "type": "worker_done",
 "from": "term_d3d1b1ea-...", "to": "run:run_5b60f88734d1",
 "subject": "...", "body": "...", "handled": false,
 "payload": {"taskId": "task_9b3742292aa2", "dispatchId": "ctx_99c9a29c9b1a"}}
```

`from` replaces `from_handle` and strips a `dispatch:` prefix, so a
terminal-less worker shows up as its bare Dispatch id. `payload` keeps only
`*Id`/`*Ids` keys (enough to match a Dispatch). There is no `sequence`
(the inbox is newest-first) and no `thread_id` (`handled` is the recipient's
read flag). `worker_asks` now matches on `from`, keeps the old keys as a
fallback, and reverses the rows instead of sorting by sequence.

## 4. `--agent omp` launches cannot reach readiness

`orca orchestration worker-start --spec ... --worktree path:<abs> --agent omp`
fails with `failedStage: agent_readiness`, `lastError: timeout`, at both a
120s and a 240s `--timeout-ms` budget (two runs, ~6 minutes total), while the
created pane sits at its composer (`π > ⟳ DeepSeek V4.1 Flash > 📁 ... > ⑂ main`).

The launch path explains it. omp's TUI config has no `composerReadyCaptures`
and no `draftPasteReadySignal`, so `hG(agent)` returns `tui-idle` and
`lnt()` waits on `waitForTerminal(condition: 'tui-idle', launchReadiness:
true)`. But:

- `orca terminal wait --for tui-idle` on a freshly created, idle omp pane
  times out (45s measured) — and on the composed worker pane too;
- the pane's output is never silent: `terminal show` reports
  `lastOutputAt` under 1s old indefinitely (status-bar repaint);
- omp's own Orca status extension posts nothing at session start
  (`~/.omp/agent/extensions/orca-agent-status.ts` registers an empty
  `session_start` handler; `before_agent_start`/`agent_start` are the first
  posts), so `worktree ps` has no row before the first turn.

A plain `terminal create --command omp` pane for the same TUI does get hook
status and `worktree ps` rows per turn (verified: `state: done`,
`toolName: bash`, `prompt` matching what was sent), so the classic lane has
everything the watcher needs.

## 5. omp's terminal title is a usable state signal

Sampled every 2s on a pane driven through one turn:

| moment  | `terminal show` title                       | preview last line |
|---------|---------------------------------------------|-------------------|
| idle    | `OMP > orca-osw`                            | `π > ⟳ DeepSeek V4.1 Flash > 📁 ... > ⑂ main ...` |
| running | `⠋ π - Run sleep command ... - orca-osw`     | `⠹ 0s > ◔ DeepSeek V4.1 Flash > 📁 ...` |
| finished| `OMP - Run sleep command ... - orca-osw`    | frame left over from the running state |

The spinner is a Braille cell in the first column; the composer band
(`> 📁 `) appears only after the TUI has rendered, which keeps a just-created
pane from counting as ready. `watcher` uses `TITLE_IDLE_PROVIDERS` for the
ready gate (`title_idle`) and to replace the output-silence guard before a
`done` row counts.

## Resulting OSW behavior

- `new omp` = `terminal create` (`omp --auto-approve ...`) + watcher; end-to-end
  smoke run finished in ~35s (ready on `title_idle` at +6s, handoff written,
  report `completion_source: ps_done`, `warning: no_tool_activity`).
- `providers.SUPERVISED_PROVIDERS` is empty; the supervised lane stays for
  records an older OSW launched (`launch_mode: supervised`), which the watcher
  still polls through `worker-show --full` and `del --close` still releases.
- `--thinking` for omp now reaches the TUI (`omp --thinking <level>` is a real
  flag); the old rejection existed only for the supervised launcher.
